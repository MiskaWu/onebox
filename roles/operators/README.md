# operators — the people who administer the host

Declares the host's administrators: one personal account each, their SSH public keys, the
OS admin group (`wheel` on RHEL-family, `sudo` on Debian/Ubuntu), the `onebox` operators
group with its sudo policy, and console-only break-glass accounts. Optionally makes a shared
checkout of this repository editable by the whole group.

```yaml
onebox_components: [operators, …]
operators_admins:
  - name: alice
    ssh_keys: ["ssh-ed25519 AAAA… alice@laptop"]
  - name: bob
    ssh_keys: ["ssh-ed25519 AAAA… bob@laptop"]
    shell: /bin/zsh
  - name: carol
    state: absent              # offboarded
operators_console_only: [rescue]
operators_repo_dir: /opt/onebox
```

## Variables

| Variable | Default | Meaning |
|---|---|---|
| `operators_admins` | `[]` | `{name, ssh_keys, shell?, state?}` (`state`: present / absent) |
| `operators_create_accounts` | `true` | create missing accounts, delete `absent` ones; `false` = only configure accounts that exist |
| `operators_group` | `onebox` | operators group; carries the sudo rule and owns `operators_repo_dir` |
| `operators_sudo_nopasswd` | `false` | sudo without a password |
| `operators_keys_dir` | `/etc/ssh/onebox_authorized_keys` | managed key files, one per user |
| `operators_console_only` | `[]` | break-glass accounts: local login only |
| `operators_repo_dir` | `""` | shared checkout of this repository (group-writable) |

Files written: `/etc/ssh/onebox_authorized_keys/<user>`, `/etc/sudoers.d/50-onebox-operators`
(checked with `visudo -cf`), `/etc/ssh/sshd_config.d/20-onebox-operators.conf` (checked with
`sshd -t`, then the effective configuration is read back with `sshd -T`).

## Why it is built like this

**Personal accounts, never a shared login.** sudo and sshd logs then say *who* ran the
destructive command, and offboarding one person is "delete one account", not "rotate the
credential everybody shares".

**Names are lowercase, enforced.** Linux names are case-sensitive and `useradd` accepts
capitals: `Alice` in the inventory would be a second, empty account (or, with account
creation off, a silently skipped person — converge green, no access). Preflight rejects
anything but `[a-z_][a-z0-9_-]*`, and with `operators_create_accounts: false` the role lists
every declared name it could not find.

**SSH keys: exclusive, but in a file of their own.** The choice between append-only and
exclusive management of `~/.ssh/authorized_keys` is a choice between two failures:
append-only can never revoke a key (removing it from the inventory changes nothing), while
rewriting the user's file exclusively locks out anyone whose working key is not in the
inventory yet — on a host where sudo needs a password, possibly with no way back in. This
role sidesteps both: the inventory's keys are written **exclusively** to
`/etc/ssh/onebox_authorized_keys/<user>` (root-owned, the user cannot add to it), and sshd is
told to read that file *in addition to* `~/.ssh/authorized_keys`:

```
AuthorizedKeysFile .ssh/authorized_keys /etc/ssh/onebox_authorized_keys/%u
```

Removing a key from the inventory revokes it on the next converge; removing a person removes
their managed file. Keys someone put into their own `~/.ssh/authorized_keys` keep working —
offboarding (`state: absent`) deletes the account, and with it that path. Public keys belong
in the inventory, in git: they are public by design, and the list is how everyone's access
comes back after the host is rebuilt. Private keys are generated by their owner and never
handled by anyone else (once someone else had it, nothing proves only its owner does).

sshd keeps the *first* `AuthorizedKeysFile` it reads, and some images ship drop-ins of their
own; the role therefore checks `sshd -T` after reloading and fails if the managed file is not
in effect.

**sudo asks for a password** (`operators_sudo_nopasswd: false`): a stolen SSH key alone is
not root, and each privileged session starts with a deliberate act. New accounts get a
*locked* password — they can log in with their key but cannot sudo until a password is set
(below). Passwords never pass through Ansible: they would end up in logs and temp files.

**Break-glass accounts** (`operators_console_only`) keep their password and sudo so someone
at the console (keyboard and screen, hypervisor or BMC console) can still repair the host
when the network path is broken — but must not be a standing, unwatched remote root path
whose actions nobody can attribute. Two locks, on purpose:
1. `DenyUsers` in the sshd drop-in rejects them *before* authentication (any key, any
   password); local logins do not go through sshd and keep working.
2. Their `~/.ssh/authorized_keys` is deleted and they get no managed key file — so if the
   drop-in is ever lost, remote access does not silently come back.

Listing an operator there would lock them out of SSH, so preflight refuses any overlap
between `operators_admins` and `operators_console_only`, and the role refuses to remove or
console-lock the account that is running the converge.

**The operators group and the repository.** Members of `onebox` get sudo through
`/etc/sudoers.d/50-onebox-operators` (explicit, independent of how the distribution's
`/etc/sudoers` treats `wheel`/`sudo`). With `operators_repo_dir`, the group shares a checkout
of this repository: `root:onebox`, mode `2775` (setgid keeps new files in the group). That
alone does not last — with umask 022 every new file is `0644`, and because git replaces files
by unlink + create, the next operator cannot even `git pull` ("Permission denied", which does
not look like a permission drift). So the role also sets `core.sharedRepository=group` (git
creates group-writable files), adds the directory to git's system-wide `safe.directory`
(git refuses to work in a directory owned by someone else), and repairs group-write on every
converge — skipping `secrets.yml` and vault password files, and files that are read-only on
purpose (git objects). Being able to edit the playbooks that root runs is root anyway; the
group just makes that explicit and attributable.

## Operations

**Onboarding** someone:
1. They generate a key pair themselves (`ssh-keygen -t ed25519`) and send the `.pub` line;
   compare the fingerprint (`ssh-keygen -lf`) over a second channel — a swapped public key is
   a backdoor you installed yourself.
2. Add the entry to `operators_admins`, `sudo make operators`.
3. Give them a password for sudo, forcing a change at first login:
   `sudo passwd alice && sudo chage -d 0 alice`. (The forced change needs an interactive
   terminal: `ssh host 'command'` fails until it is done.) Suggested target:
   `make operator-password USER=alice`.
4. They log in on the admin SSH port (`common_admin_ssh_port`) and check `id` (groups) and
   `sudo -v`.

**Offboarding**: set `state: absent` (keeps the history in git: who removed whom), converge.
The account is deleted and its managed keys removed; the home directory stays until you
decide it is no longer needed (`sudo rm -rf /home/<name>`; files elsewhere still owned by the
old uid: `find / -xdev -nouser`). Rotate every secret the person could read — any operator
with sudo could read them all at run time, whatever is encrypted at rest.

**Status**: `getent group onebox`, `sudo sshd -T | grep -E '^(authorizedkeysfile|denyusers)'`,
`passwd -S <name>`. Suggested target: `make operator-status`.

## Pitfalls

- **Socket-activated sshd (Ubuntu 24.04+)**: the role reloads sshd with
  `systemctl try-reload-or-restart`, which does nothing when `ssh.service` is not running —
  the next connection starts it with the new configuration. Starting `ssh.service` by hand
  there would fight `ssh.socket` for the port.
- **A key wrapped over two lines, or the private key** pasted instead of the `.pub` line, is
  rejected by preflight. If a private key was pasted anywhere, treat it as leaked.
- **SELinux**: the managed key files live under `/etc/ssh`, readable by sshd in the default
  policy. If logins with a managed key fail with "Authentication refused" while the file is
  right, check `ls -Z /etc/ssh/onebox_authorized_keys` and run `restorecon -Rv` on it.
- Accounts created by this role use `/bin/bash` unless `shell` is set; on Debian, plain
  `useradd` would default to `/bin/sh`.
- **Offboarding someone who is still logged in** fails (`userdel` refuses while the account
  has processes). End their sessions first: `loginctl terminate-user <name>`. Do not use
  `pkill -u`: rootful containers without user-namespace mapping run as host uids, and a
  container process may share a uid with a person's account.
